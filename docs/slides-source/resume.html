When something breaks

Killed mid-run

Rows already decided are saved. The next sync does only the rest.

Model call fails

The run stops with an error. Rows stay new. Run sync again.

Ledger is down

The row stays approved with the error saved. It is posted first next time.

Crash after a post

The same ID is sent again. The ledger says already there. No duplicate.

Handle same transaction, same ID

Two identical coffees, same day. Both rows read:

Checking | 2026-10-03 | -5.75
SQ *BLUE BOTTLE 0423 SF

So we add n, the count of identical rows before this one. Different n, different ID:

n=0 txn-8b3c6f4d03659c9e079e
n=1 txn-32775b79e1ed17875fea

The ID is a SHA-256 fingerprint of the fields plus n: same input, same ID.

Load the same file again: same IDs, rows skipped. Nothing is added twice.

The one idea on this slide: you can stop it at any point and run it again. The reason is the internal SQL database, a SQLite file. Every transaction is one row with a state, new, needs review, approved, posted, and every step is saved the moment it happens, so nothing important lives only in memory. A crash or a kill cannot lose finished work. The table below it is what happens in each failure. For the ID on the right, start with the example: two real identical coffees on the same day read exactly the same, so the ID cannot come from the fields alone. We add n, how many identical rows came before this one, so the first coffee is n=0 and the second is n=1, and they get different IDs and both are kept. The ID is a SHA-256 fingerprint of the account, the date, the amount in cents and the description (trimmed, upper-cased, spaces collapsed) plus n. SHA-256 is a fingerprint function: the same input always gives the same output. So loading the same file again gives the same IDs and the rows are skipped. The ledger number is the first 20 characters of that fingerprint, saved at the first post attempt and never recomputed, so after a crash the retry sends the same number and the ledger rejects it as already there. If asked for evidence: I killed a real sync after 7 of 19 rows were decided, and the rerun did the other 12 with zero duplicates. The ledger-down case is covered by tests.
